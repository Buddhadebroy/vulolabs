# Google Connect broker — contract for VuloCloud

`VuloPilot\Services\GoogleServicesConnection` (this plugin) can route
"Connect Google Services" through a VuloCloud-hosted broker instead of
talking to `accounts.google.com` directly, once
`VULOPILOT_GOOGLE_BROKER_URL` is set (`config.php`). This is the same
shape RankMath's own Google Connect uses, and is the real fix for the
"Redirect URI scaling" trade-off documented in that same file: Google
OAuth Clients only accept a fixed, pre-registered allowlist of redirect
URIs, and with today's embedded shared Client
(`VULOPILOT_GOOGLE_CLIENT_ID`/`SECRET`), only domains someone has
manually added to that Client's allowlist in Google Cloud Console can
complete the handshake. With a broker, Google only ever sees VuloCloud's
own single, permanently-registered redirect URI — any customer domain
works with zero manual allowlisting.

This document is the contract the WordPress side (already implemented —
`GoogleServicesConnection`, `GoogleOAuthBrokerClient`,
`GoogleSearchConsoleOAuthCallbackHandler`) expects VuloCloud's server
side to implement. Nothing here exists on the VuloCloud side yet — this
is the spec to build against, not a description of something already
running.

## Actors and the full round trip

1. A site owner clicks "Connect Google Services" on their WordPress
   install (`vulopilot`). Their browser navigates to VuloCloud:
   `GET {VULOPILOT_GOOGLE_BROKER_URL}/plugin/google/authorize`.
2. VuloCloud 302s the browser to `https://accounts.google.com/o/oauth2/v2/auth`
   using **its own** registered Google Cloud OAuth Client (Client
   ID/Secret VuloCloud owns, never shipped to any WordPress install) and
   **its own** fixed `redirect_uri` (the only one ever registered in
   Google Cloud Console).
3. The site owner consents on Google's real consent screen.
4. Google redirects back to VuloCloud's fixed callback with a `code`.
5. VuloCloud exchanges that `code` with Google server-to-server, then
   302s the browser back to the **original WordPress site's own**
   callback URL (captured in step 1) with a new, VuloCloud-issued
   `code` — NOT Google's code, and NOT the tokens themselves (tokens
   never touch the browser/URL bar).
6. The WordPress site's callback
   (`GoogleSearchConsoleOAuthCallbackHandler::handle_callback()`) calls
   VuloCloud server-to-server: `POST /plugin/google/exchange`, trading
   that code for the real Google `access_token`/`refresh_token`, which it
   then encrypts and stores locally (`GoogleServicesConnection`) — same
   storage shape as the direct-to-Google flow.
7. Later, when the stored access token expires, the WordPress site calls
   `POST /plugin/google/refresh` server-to-server to get a new one — a
   broker-issued `refresh_token` is only valid against VuloCloud's own
   OAuth Client, so it cannot be refreshed by calling Google directly
   with the embedded shared Client's credentials.

VuloCloud never needs to store Google tokens long-term for this flow —
steps 5–7 only need a short-lived correlation record (the `authorize`
call's `domain`/`return_uri`/`state`) and a short-lived, single-use
exchange code. The real, long-lived Google tokens end up stored on the
WordPress site itself, exactly as they do today.

## Endpoints VuloCloud must implement

### `GET /plugin/google/authorize`

Query params (from `GoogleOAuthBrokerClient::get_authorize_url()`):

| param | meaning |
|---|---|
| `domain` | The WordPress site's own `home_url()` — used only as a correlation key, not trusted for anything security-sensitive (see Security notes). |
| `return_uri` | The WordPress site's own OAuth callback (`admin-post.php?action=vulopilot_gsc_oauth_callback`) — where VuloCloud must redirect the browser back to once Google's handshake completes. |
| `state` | An opaque value generated by the WordPress site (a real WP nonce + `return_to` target, base64'd JSON) — VuloCloud must **echo this back verbatim** on the final redirect (step 5) and never inspect/decode it. It is the WordPress site's own CSRF guard, not VuloCloud's. |

Behavior: record `{domain, return_uri, state}` against a short-lived
server-generated correlation id (this becomes VuloCloud's own OAuth
`state` sent to Google in step 2 — Google's `state` round-trips through
Google unmodified, same mechanic this plugin's own direct-flow code
already relies on). Then `302` to Google's real authorize URL using
VuloCloud's Client ID, `redirect_uri` = VuloCloud's own fixed callback,
and the scopes below.

Required scopes (must match `GoogleServicesConnection::SCOPES` exactly,
so whatever this endpoint requests, VuloCloud must actually forward):

```
https://www.googleapis.com/auth/webmasters.readonly
https://www.googleapis.com/auth/analytics.readonly
https://www.googleapis.com/auth/adsense.readonly
```

Also pass `access_type=offline&prompt=consent` to Google, same reason
`GoogleServicesConnection::get_authorization_url()`'s own docblock
gives: Google only issues a `refresh_token` on first consent unless
`prompt=consent` forces it on every authorization.

### VuloCloud's own Google callback (internal, no WordPress-side contract)

Whatever fixed path VuloCloud registers with Google. On success, look up
the correlation record from step 1 by Google's returned `state`,
exchange Google's `code` for tokens using VuloCloud's Client
Secret, generate a new short-lived single-use exchange code, store
`{domain, tokens}` against it (TTL a few minutes is enough — the
WordPress site calls `/plugin/google/exchange` immediately after this
redirect), then:

`302 {return_uri}?code={new_exchange_code}&state={original site state, verbatim}`

On failure (user denies consent, Google returns an error): redirect the
same way but with `?error=access_denied` (or whatever code) instead of
`code=` — `GoogleSearchConsoleOAuthCallbackHandler::handle_callback()`
already handles an `error` param the same way it does today for the
direct flow.

### `POST /plugin/google/exchange`

Request body (`GoogleOAuthBrokerClient::exchange()`):

```json
{ "domain": "https://customer-site.example", "code": "<exchange code from the redirect above>" }
```

Behavior: look up the stored `{domain, tokens}` record by `code`
(single-use — invalidate it immediately after this call, whether or not
it succeeds). Optionally cross-check `domain` matches what was recorded
in step 1 as defense-in-depth (see Security notes — this is not the real
security boundary, the code's own unguessability/single-use/short TTL
is).

Response, `200`:

```json
{
  "access_token": "ya29....",
  "refresh_token": "1//....",
  "expires_in": 3599
}
```

`refresh_token` may be omitted/empty if Google didn't return one on this
particular consent (matches `GoogleOAuthBrokerClient::exchange()`'s own
handling — same caveat the direct flow already documents).

Response, failure: any non-2xx with a JSON body `{"message": "..."}` (or
`{"error": "..."}`) — `GoogleOAuthBrokerClient` surfaces either as the
`WP_Error` message shown to the site owner.

### `POST /plugin/google/refresh`

Request body (`GoogleOAuthBrokerClient::refresh()`):

```json
{ "domain": "https://customer-site.example", "refresh_token": "1//...." }
```

Behavior: call Google's own `POST https://oauth2.googleapis.com/token`
with `grant_type=refresh_token` using VuloCloud's Client ID/Secret and
the given `refresh_token`.

Response, `200`:

```json
{ "access_token": "ya29....", "expires_in": 3599 }
```

(No `refresh_token` in the response — Google doesn't rotate it on a
refresh grant, so the WordPress site keeps using the one it already has
stored.)

Response, failure: same shape as `/exchange` above.

## Security notes

- **The WordPress site's own `state` value is its real CSRF guard** —
  VuloCloud must treat it as an opaque blob to echo back, never as
  something it authenticates against. Don't skip forwarding it; don't
  attempt to parse it.
- **`domain` is a correlation/UX convenience, not an authorization
  check.** Nothing stops a caller from lying about it — the actual
  security boundary is that `/plugin/google/authorize`'s `return_uri` is
  where VuloCloud redirects the completed handshake, and
  `/plugin/google/exchange`'s `code` is unguessable, single-use, and
  short-TTL. Do not use `domain` alone to decide whether to hand back
  tokens.
- **`return_uri` should be validated as a URL VuloCloud is willing to
  redirect to** (e.g. reject `javascript:`/non-http(s) schemes) — it's
  attacker-influenced input (any WordPress site can call `/authorize`
  with any `return_uri`), so this is a real open-redirect surface if
  unchecked, same as any OAuth broker's `redirect_uri` parameter.
- VuloCloud's Client Secret must never appear in any response to the
  WordPress site — only `access_token`/`refresh_token` values, exactly
  like the endpoints above already specify.

## What does NOT change on the WordPress side

Everything downstream of "we have a valid access token" is identical
regardless of direct-vs-broker: `list_search_console_sites()`,
`GoogleAnalyticsClient`, `GoogleAdSenseClient`, the REST controller
(`Controllers\GoogleServices`), and every React panel consuming it. The
branch lives entirely inside `GoogleServicesConnection` (`has_broker()`,
`get_authorization_url()`, `exchange_broker_code_for_tokens()`,
`refresh_access_token()`) and the new `GoogleOAuthBrokerClient` — no
other file needed to change.
